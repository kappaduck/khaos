# Code source builder

Draft, 2026-11-25. Internal to `analyzers/`: no game sees it. It is the text writer that every Khaos source generator
uses (`analyzers/Shared/CodeSourceBuilder.cs`).

## The idea

A source generator ends by writing C# as text and handing it to Roslyn. Duck did it with `SourceBuilder`
(`K:\duck\analyzers\Shared\SourceBuilder.cs`), a `StringBuilder` with an indentation level, `\n` line endings, the
`// <auto-generated/>` header and `using` blocks that close their brace. It works, and its output is right.

Its cost lies in the call sites. Each line is an interpolated string:

```csharp
builder.AppendLine($"private readonly {@case.TypeName} {ManagedField(@case)};");
```

The analyzers target `netstandard2.0`, where the compiler turns that `$"..."` into `string.Concat` or `string.Format`
([C# reference, interpolated strings][interpolated]). It builds a temporary `string` for every line, and boxes every
`int` in the line, before `StringBuilder` copies it. The `DefaultInterpolatedStringHandler` that avoids this on .NET 6
and later is not in `netstandard2.0`.

The question was: since spans work in `netstandard2.0`, can a builder of our own do better than `StringBuilder`?
Partly. Spans are there (System.Memory 4.6.3 and System.Buffers 4.6.1 come with Microsoft.CodeAnalysis, see
`artifacts/obj/Khaos.Analyzers/project.assets.json`). But `StringBuilder` in `netstandard2.0` cannot take them:
`Append(ReadOnlySpan<char>)` exists from .NET Standard 2.1 on ([StringBuilder.Append][sb-append]). No polyfill can add
an overload to a type of the reference assembly. Most of the gain comes from somewhere else, an interpolated string
handler of our own, and that works with either storage.

## In use

What a generator writes, with the recommended builder (design C below):

```csharp
private static string Emit(UnionModel union)
{
    using CodeSourceBuilder builder = new();   // rents its buffer, writes the header

    builder.AppendLine($"namespace {union.Namespace};")
           .AppendLine();

    using (builder.AppendBlock($"partial struct {union.Name}"))
    {
        builder.AppendLine($"private readonly byte {TagField};");

        for (int i = 0; i < union.Cases.Length; i++)
            builder.AppendLine($"private const byte Tag{i} = {i + 1};");   // int holes: no boxing
    }

    return builder.ToString();                 // the one string Roslyn needs
}

context.RegisterSourceOutput(unions, static (output, union) =>
    output.AddSource($"{union.Name}.g.cs", SourceText.From(Emit(union), Encoding.UTF8)));
```

The call sites look exactly like duck's. Only the builder changes, so porting `UnionEmitter` and the three duck
generators does not rewrite them.

What the generator writes, unchanged from duck:

```csharp
// <auto-generated/>
#nullable enable

namespace Game;

partial struct Shape
{
    private readonly byte _tag;
    private const byte Tag0 = 1;
}
```

The builder's shape, as the generators see it (signatures only):

```csharp
internal sealed class CodeSourceBuilder : IDisposable
{
    internal CodeSourceBuilder Append(string text);
    internal CodeSourceBuilder Append(ReadOnlySpan<char> text);
    internal CodeSourceBuilder Append([InterpolatedStringHandlerArgument("")] ref LineHandler text);

    internal CodeSourceBuilder AppendLine();
    internal CodeSourceBuilder AppendLine(string line);
    internal CodeSourceBuilder AppendLine(ReadOnlySpan<char> line);
    internal CodeSourceBuilder AppendLine([InterpolatedStringHandlerArgument("")] ref LineHandler line);

    internal Block AppendBlock([InterpolatedStringHandlerArgument("")] ref LineHandler line);
    internal Block AppendBlock([InterpolatedStringHandlerArgument("")] ref LineHandler line, string closing);

    public override string ToString();
    public void Dispose();

    [InterpolatedStringHandler]
    internal ref struct LineHandler   // writes each piece straight into the buffer, through the same path as Append
    {
        public LineHandler(int literalLength, int formattedCount, CodeSourceBuilder builder);
        public void AppendLiteral(string value);
        public void AppendFormatted(string? value);
        public void AppendFormatted(ReadOnlySpan<char> value);
        public void AppendFormatted(char value);
        public void AppendFormatted(int value);
    }

    internal readonly ref struct Block : IDisposable { }
}
```

When an argument is an interpolated string, C# picks the handler overload over `AppendLine(string)`, as
`StringBuilder.Append` does on .NET 6 and later
([dotnet/runtime StringBuilder.cs][sb-source]). A string with no holes, or a constant one, still goes to
`AppendLine(string)`.

`Append` and `AppendLine` follow the .NET convention of `StringBuilder.Append` and `AppendLine`, or `TextWriter.Write`
and `WriteLine` ([StringBuilder.AppendLine][sb-appendline]). `Append` writes part of a line, and `AppendLine` writes
its text and always ends the line. A caller never writes `"\n"` itself. The one difference from .NET is the line
ending, always `\n` instead of `Environment.NewLine`, so the generated code is the same on Windows and Linux.

`Append` is for a line built in a loop. Duck's input generator joined the bindings first, with three allocations for
one line (`ToArray`, `string.Join`, `+`, in `InputActionsGenerator.cs`). With `Append`:

```csharp
builder.Append($"public static InputAction {action.Name} {{ get; }} = new({action.Id}");

foreach (string binding in action.Bindings.AsSpan())
    builder.Append($", {binding}");

builder.AppendLine(");");
```

## Cases to cover

| Case | What the generator author sees |
| :--- | :--- |
| A line inside nested blocks | Indented 4 spaces per level, like duck and the runtime's `SourceWriter` |
| `AppendLine()` or `AppendLine("")` | A bare `\n`, no trailing spaces |
| A line built from several `Append` calls, ended by `AppendLine` | Indented once, at its first character: the same text as one `AppendLine` |
| `Append` never followed by `AppendLine` | The text ends without a `\n`. No assert: the tests of each generator catch it |
| `AppendBlock` after an `Append` on the same line | Its text continues that line, as `AppendLine` does, then `{` goes on the next line. The handler writes the text before `AppendBlock` runs, so it could not end the line first |
| Line endings | Always `\n`, on Windows too (the commented test in `CodeSourceBuilderTests`) |
| A hole that is a `string`, a span, a `char` or an `int` | Written in place: no temporary string, no boxing |
| A hole of another type (`bool`, an enum) | No overload: a build error, so the author writes `value ? "true" : "false"` or a name. An overload is added when a generator needs one |
| A line that holds a `\n` (a doc comment pasted whole, a raw string literal) | Each line is indented, see below |
| A `\r` in a line or a hole | Dropped: the output stays `\n` whatever the input |
| A file longer than the first buffer (1,024 chars) | The buffer grows: rent twice the size, copy, return the old one |
| An exception in the middle of `Emit` | `using` returns the buffer; the generator fails as it would today |
| `Dispose` forgotten | No leak: the GC collects the array, it just does not go back to the pool |
| Written to after `Dispose` | `ObjectDisposedException`, never a write into an array another builder now holds |
| `ToString()` after `Dispose` | `string.Empty`, no exception: `ToString` must not throw, since the debugger calls it (CA1065, [rule][ca1065]) |
| Blocks left open at `ToString()` | No assert, unlike the runtime's `SourceWriter`: the debugger calls `ToString()` in the middle of a build, and an assert in `Dispose` would fire on the exception path too. The snapshot tests catch it |
| Two outputs emitted at once on two threads | One builder each; `ArrayPool<char>.Shared` is thread-safe ([ArrayPool][arraypool]) |

`StringBuilder` knows nothing of lines. `Append` copies the characters as they are, and `AppendLine` adds
`Environment.NewLine`, `\r\n` on Windows ([StringBuilder.AppendLine][sb-appendline]). That is why duck's builder,
given a line with a `\n` inside two blocks deep, indents only the first line:

```csharp
builder.AppendLine("/// <summary>\n/// Holds one shape.\n/// </summary>");
```

```text
        /// <summary>
/// Holds one shape.
/// </summary>
```

Ours writes the indentation when a line starts, not when `AppendLine` is called. Whatever it writes, a literal, a
hole or a span, it looks for the next `\r` or `\n` and copies each segment in one piece. Before the first character
of a line it writes the indentation, so an empty line stays empty, without trailing spaces. The same call gives:

```text
        /// <summary>
        /// Holds one shape.
        /// </summary>
```

On cost: this is not a per-frame path. An output reruns only when its model changes, which the cookbook keeps rare
through value-equatable models ([incremental generators cookbook][cookbook]). It runs on edits in the IDE and on each
build, though, so a few kilobytes less per output is worth having as long as it costs little to write.

## Other designs

### A. Keep duck's `SourceBuilder`

```csharp
builder.AppendLine($"private readonly byte {TagField};");   // string.Concat: one temporary string
```

Already written and tested, and it is exactly what the Roslyn cookbook advises: "a wrapper around StringBuilder that
will keep track of indent level" ([cookbook][cookbook]). The runtime's own generators (System.Text.Json, logging,
configuration) do the same in `SourceWriter` ([source][sourcewriter]). It loses only on allocations: one string per
line, a box per `int`.

### B. `StringBuilder` + our handler

The same `LineHandler`, but writing into a `StringBuilder`. It removes the temporary strings, so it gets almost all of
C's gain with less code: no buffer to grow or return. It loses on spans. `AppendFormatted(ReadOnlySpan<char>)` and
`AppendLine(ReadOnlySpan<char>)` would have to go through `fixed` and `StringBuilder.Append(char*, int)`, the way the
runtime's `SourceWriter` does with its comment "There is no StringBuilder.Append(ReadOnlySpan<char>) overload in the
NS2.0" ([source][sourcewriter]). That means `unsafe` in the analyzers.

### C. Our pooled `char[]` + our handler

A `char[]` rented from `ArrayPool<char>.Shared`, our own length, the handler writing into it. CommunityToolkit's MVVM
generators work the same way: `ImmutableArrayBuilder<T>` rents 1,024 chars, grows by renting again and returns the
array on `Dispose` ([source][toolkit-builder]).

It is a `sealed class`, not a `ref struct`. `Block` must keep a reference to the builder in order to close its brace,
and a `ref struct` can only hold another one through a `ref` field, which `netstandard2.0` does not support (CS9064,
"Target runtime doesn't support ref fields", [compiler errors][cs9064]). CommunityToolkit's builder hits the same
limit, which is why it is a `ref struct` wrapped around a `Writer` class.

### D. Wait for Roslyn's `IndentingStringBuilder`

dotnet/roslyn#71162 proposes exactly this type, public, with an interpolated handler and `GetSourceTextAndClear()`.
It is open, labelled `api-needs-work`, in the Backlog. In May 2025 a maintainer said it is still considered, and
that nobody is working on it ([issue][roslyn-71162]). Nothing to adopt for now. If it ships, it needs a Roslyn newer than the 5.12 that Khaos pins
(`Directory.Packages.props`).

### The recommendation

**C**, for these reasons:

1. **The handler is the real gain, and A has none.** B and C both remove the temporary string of every line, and the
   boxing of `int` holes.
2. **Spans without `unsafe`.** With our own array, `AppendLine(ReadOnlySpan<char>)` is a `CopyTo`. B needs pointers
   for the same thing, in code that should stay simple.
3. **One buffer, reused.** Each rerun takes its array back from the pool instead of growing a new `StringBuilder` in
   chunks. That suits the IDE, where outputs rerun often.
4. **Small to write.** It adds growth and `Dispose` compared with B, about twenty lines. CommunityToolkit shows the
   pattern holds up in a widely used generator.

The risk is the one every pooled buffer carries: writing after `Dispose` into an array the pool has handed to someone
else. Clearing the field on `Dispose` and throwing afterward turns that into an exception.

Challenge to the recommendation itself: the gain is a few kilobytes per output, and duck's builder is good enough for
the cookbook. If the measurement below shows B and C within noise of each other, B wins by being simpler. If both are
within noise of A, then A wins.

Not a game-engine topic: Godot, Unity, MonoGame and raylib do not generate C# this way. The useful comparisons are
other generators:

| Project | Builder | Storage | Handler |
| :--- | :--- | :--- | :--- |
| dotnet/runtime (`SourceWriter`) | class | `StringBuilder` | No; spans through `char*` |
| CommunityToolkit MVVM | `ImmutableArrayBuilder<char>` | pooled `char[]` | Not in the files I could open |
| Roslyn proposal #71162 | struct | not settled | Yes |

## Building blocks

All .NET, nothing native.

- [Custom interpolated string handlers][handler-tutorial]: the pattern (`[InterpolatedStringHandler]`, a constructor
  `(int literalLength, int formattedCount, ...)`, `AppendLiteral`, `AppendFormatted`). It is a compiler feature;
  PolySharp, already in the analyzers, supplies the two attributes for `netstandard2.0` (its package page lists
  "Interpolated string handlers", [PolySharp][polysharp]).
- [`ArrayPool<T>`][arraypool] from System.Buffers, and `Span<T>`/`ReadOnlySpan<T>` from System.Memory: both come with
  Microsoft.CodeAnalysis.
- [`SourceText.From`][sourcetext]: no `char[]` or span overload (string, `Stream`, `byte[]`, `TextReader` with a
  length). One `ToString()` at the end is the normal path.
- No `int` formatting into a span in `netstandard2.0` (no `ISpanFormattable`): `AppendFormatted(int)` writes its
  digits by hand, a short loop.

## Measuring

A, B and C are compared before the storage is chosen:

- A BenchmarkDotNet run with `[MemoryDiagnoser]` that emits the same file through each builder, the port of
  `UnionEmitter` with a union of a few cases. `performance/benchmarks/` does not exist yet in this repository.
- An allocation test in `Khaos.Analyzers.Tests` on the chosen builder (`GC.GetAllocatedBytesForCurrentThread()` around
  one emission), so a regression shows up in the tests.
- The Verify snapshot in `CodeSourceBuilderTests` keeps the output the same, byte for byte, through the change.

## Decided

2026-11-25, by Alexandre. The storage (A, B or C) waits for the measurement.

- **A line that holds `\n` is split**, and each line gets the indentation, from literals and holes alike. `\r` is
  dropped. It is what the runtime's `SourceWriter` does, and duck's builder left every line after the first at
  column 0.
- **Holes: `string`, `ReadOnlySpan<char>`, `char` and `int`.** Another type fails to build, and an overload is added
  when a generator needs it. No generic `AppendFormatted<T>`: on `netstandard2.0` it could only call `ToString()`.
- **`Append` and `AppendLine`**, as in .NET: `Append` writes part of a line, and `AppendLine` always ends it with `\n`.
  The indentation is written at the first character of a line, so a line built from several calls comes out the same
  as one written in a single call. `AppendBlock` continues the current line too: its handler has written the text
  before the method runs.
- **No asserts.** Not in `ToString()`, which the debugger calls in the middle of a build, nor in `Dispose`, which also
  runs when a generator throws. An open block or an unfinished line shows up in the snapshot tests.
- **The header is fixed**: `// <auto-generated/>`, `#nullable enable`, a blank line.
- **The result comes from `ToString()`**, as for `StringBuilder` and CommunityToolkit's `ImmutableArrayBuilder<T>`.
  `Build()` is the habit of hosts and configuration builders, which produce an object rather than text. `ToString()`
  also shows the code in the debugger, which is why it returns `string.Empty` after `Dispose` instead of throwing.
